## 一、实验过程（20 分）

本实验包含四个程序：`process1` 持续打印；`process2` 创建一个子进程，父子各打印 999 次；`process3` 的父进程打印完退出、子进程无限循环；`process4` 的父子进程均无限循环。通过 `ps`、`top` 记录 PID、PPID、状态、CPU 占有率和驻留内存，再用信号终止自己启动的进程。

本次维护为三个 `fork()` 补上失败检查，删除未使用变量。`process2` 显式使用行缓冲，便于完整统计父子输出；两个无限循环变体仍保留题目的执行结构，不增加 `wait()`，以免改变观察对象。无限输出丢弃到 `/dev/null`，不再写入可能迅速膨胀的临时文件。

单独观察任务一可以执行：

```sh
./build/lab1/process1 > /dev/null &
pid=$!
ps -o pid,ppid,stat,pcpu,pmem,rss,comm -p "$pid"
LC_ALL=C top -b -n 1 -p "$pid"     # 批处理；不带 -b 的 top 才是交互界面
kill -TERM "$pid"
wait "$pid" || true               # shell 回收该后台进程
ps -p "$pid"
```

## 三、实验结果及分析（30 分）

### 1. 任务一：观察并终止进程

![任务一运行记录排版图，非原始终端截图](shots/lab1_task1.png)

{{text:lab1_task1.txt}}

记录列出了实际 PID、状态、CPU 和 RSS；发送终止信号并回收后，该测试会话中已无进程。`ps` 的 CPU 百分比是其统计口径下的平均值，`top` 的数值受采样间隔影响，二者不必相等。`%MEM` 显示 0.0 是比例较小且显示精度有限，不表示完全不占内存。

**思考题**：循环最直接影响的是 CPU 使用，而 PID 不随循环变化。本例没有在循环中持续申请内存，内存使用通常相对稳定。`printf()` 先操作 stdio 缓冲，并非每调用一次都执行一次 `write()`；输出到终端或管道时还可能因 I/O 阻塞，不能保证始终为 R 态。本次重定向到 `/dev/null` 后，循环通常能消耗接近一个逻辑 CPU 的时间。可通过阻塞等待事件、加入合理延时或限速降低忙等消耗。CPU 需要调度和资源控制，但普通进程的忙循环并不等于系统必然无法工作，内核仍能抢占它。

### 2. 任务二：父子各 999 次输出

![任务二运行记录排版图，非原始终端截图](shots/lab1_task2.png)

{{text:lab1_task2.txt}}

采集器读取到所有标准输出写端关闭，再对完整数据计数：父进程 999 行、子进程 999 行，共 1998 行。图中只展示开头片段，统计不是对片段进行的。程序显式设为行缓冲，因此重定向采集时仍逐行刷新；这与题目原始版本通常在文件/管道上使用全缓冲有所区别。

父子没有规定谁先执行或必须交替。调度、CPU 核数、输出设备和缓冲策略共同影响可见顺序；多核上还可能同时运行，不能把每次相邻输出都解释为一次时间片切换。行缓冲不构成业务同步，也不保证严格逐行交替。默认全缓冲的具体容量由实现与环境决定，不能概括为恒定 4 KB。

### 3. 变体一：父进程退出，子进程继续运行

![变体一运行记录排版图，非原始终端截图](shots/lab1_task3.png)

{{text:lab1_task3.txt}}

父进程正常退出后，原子进程仍在无限循环；本次它的 PPID 变为测试器的 PID，因为测试器显式设置了 subreaper。一般 Linux 环境中，孤儿会由适用的 subreaper 或所在 PID 命名空间的 init 收养，不能仅凭一个 PPID 数字断定具体程序。父进程结束不自动终止子进程。这里丢弃了循环输出，未统计子进程打印量，也不再沿用旧记录中缺一行的未经验证解释。

### 4. 变体二：父子均不会主动结束

![变体二运行记录排版图，非原始终端截图](shots/lab1_task4.png)

{{text:lab1_task4.txt}}

两条进程记录中，一条的 PPID 为另一条的 PID，说明父子仍同时存在。它们可在多核并行，也可竞争同一 CPU；实际使用率受负载、亲和性、配额与采样时长影响，不保证各占满一个核心。输出行数相近不能单独证明调度公平。本次按进程组结束两者，确认无测试进程残留。

## 四、疑难小结（20 分）

1. 无限打印不能通过无限写日志来观察。短时运行、`/dev/null` 和按 PID/进程组采样可限制资源消耗。
2. `head` 提前退出会关闭管道读端，后续写入可能触发 SIGPIPE，不能用于验证完整的 999 次循环；本次统计读取至 EOF。
3. `kill` 发出信号不等于立即回收。进程结束、父进程执行等待和 `ps` 采样是不同事件，需要分别确认。
4. 本次实际修复了 `fork()` 失败分支和无用变量；缓冲、并发顺序与孤儿收养的解释也已按复测方式修正。不补写无法核实的历史调试经历。
